# Independent Adversarial Review Gate

This module owns the single code review/fix loop. Git operations check its result; contribution handling enters it for code changes without maintaining another loop. Apply the entrypoint's stage-specific specialist-selection rules before dispatch; no named review skill is required.

The plan gate in planning.md applies to exactly the same source/script/test change scope, before edits. This module remains the post-implementation gate; a clean plan review does not replace it.

## Mandatory Independent Adversarial Review

After completing a code change, run this loop before reporting the code work complete and before every commit containing code changes. It applies to source, scripts and tests at every risk level, including small and behavior-preserving changes. Local-only work still requires the loop before claiming completion; the loop itself grants no commit or push authority. Content-only tasks that change no code do not trigger it.

1. Freeze the task baseline, attributable paths, overall goal, exclusions and confirmed acceptance conditions. Include the full accumulated task change, affected callers and contracts, and in-scope new files. Inspect staged and unstaged layers separately so worktree edits cannot hide different code in the index.
2. Start a new independent subagent for the round, with a fresh context rather than the implementer's conversation. Have it check the available skill descriptions and preferably use a suitable review specialist; no specific skill name is required. With none suitable, it performs the review directly under this contract. Give it the original requirements, applicable project rules, baseline, exact current change and relevant code. Do not lead it with an intended verdict, earlier review conclusions or the implementer's defense. The subagent reviews read-only and attempts to disprove correctness through realistic failure cases: regressions, boundary behavior, security, state, concurrency, compatibility and inadequate verification. Require each actionable finding to cite file/lines, evidence and impact; unsupported suspicions and style preferences are not findings.
3. At the start of every round and before each fix, compare the full accumulated change and proposed fix with the overall goal, exclusions and confirmed acceptance conditions. Assess findings against current code and those requirements. Reject scope drift and defer unrelated improvements; do not grow scope merely because another review round found an opportunity. Clarify dependent goal or scope changes with the user. Re-enter planning.md when a valid fix materially changes the reviewed approach, affected boundaries or verification strategy. Fix every valid in-scope issue and run the relevant checks. Record evidence for false positives or already-correct behavior; report unrelated pre-existing issues without expanding scope. An unresolved issue affecting the changed contract blocks completion and commit, even if its repair needs additional scope or a user decision.
4. After any fix, start another fresh subagent to review the entire accumulated change again, including all earlier fixes. Do not review only the latest patch. There is no limit on review rounds. End the loop only when the latest complete subagent review finds no new valid in-scope issues and every previously identified valid in-scope issue has been resolved, including issues introduced by fixes. A round with no new issues is not clean if an earlier valid issue remains unresolved. Required verification must also pass before completion or commit.
5. Bind the clean review to the exact reviewed content and intended commit payload. Reinspect the full index before committing; any later code change, fix, or staged payload difference invalidates the clean result and restarts the loop. Mere staging of identical reviewed content does not require another round. Retain round identity, findings/dispositions, fixes, checks and reviewed content fingerprint in the external task record or, for Light work, a concise conversation record.

Use real subagent delegation; inline self-review cannot substitute. If delegation is unavailable, a review is partial, verification fails, intent is uncertain, or repeated attempts cannot progress, stop without committing and report the concrete blocker. Never treat a round limit, elapsed time or an unchanged repeated finding as a clean result. Material uncertainty requires clarification rather than guessing. A read-only reviewer never fixes or publishes; the parent implements authorized fixes and requests a new review.
