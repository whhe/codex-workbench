# Independent Adversarial Review Gate

This module owns the single independent review/fix loop for all file change types. Git and contribution paths use this loop. Apply the entrypoint's stage-specific specialist-selection rules before dispatch; no named review skill is required.

Use planning.md before authoring file changes. Use this gate on the resulting file changes, including existing changes selected for commit.

## Mandatory Independent Adversarial Review

Run this loop before reporting file changes complete or committing them. Cover all types and sizes of file changes, including documentation, skills, configuration and assets. Use the same gate for local-only work. Skip this gate when there are no file changes, including remote replies, title/body updates and thread transitions alone. Review grants no commit, push or publication authority.

1. Freeze the task baseline, scope, goal, exclusions and acceptance conditions. Supply the full accumulated change and affected context. Include additions, deletions, renames and mode changes. Inspect staged and unstaged layers separately in Git. Review the exact intended file change payload before each commit.
2. Start a new independent subagent for the round, with a fresh context rather than the implementer's conversation. Have it check the available skill descriptions and preferably use a suitable review specialist; no specific skill name is required. With none suitable, it performs the review directly under this contract. Give it the original requirements, applicable project rules, baseline, exact current change and relevant context. Do not lead it with an intended verdict, earlier review conclusions or the implementer's defense. The subagent reviews read-only and attempts to disprove correctness through failure cases appropriate to the change, such as factual errors, conflicting instructions, regressions or inadequate verification. Require each actionable finding to cite a precise location, evidence and impact; unsupported suspicions and style preferences are not findings.
3. At the start of every round and before each fix, compare the full accumulated change and proposed fix with the overall goal, exclusions and confirmed acceptance conditions. Assess findings against current evidence and those requirements. Apply the entrypoint's Minimum Necessary Change to every proposed remedy and the accumulated diff, including cross-project delivery costs. Prefer removing an unnecessary addition over repairing its self-created complexity when the original acceptance conditions still hold. Reject scope drift and defer unrelated improvements; do not grow scope merely because another review round found an opportunity. Clarify dependent goal or scope changes with the user. Re-enter planning.md when a valid fix materially changes the reviewed approach, affected boundaries or verification strategy. Fix every valid in-scope issue and run the relevant checks. Record evidence for false positives or already-correct behavior; report unrelated pre-existing issues without expanding scope. An unresolved issue affecting the changed contract blocks completion and commit, even if its repair needs additional scope or a user decision.
4. After any fix, start another fresh subagent to review the entire accumulated change again, including all earlier fixes. Do not review only the latest patch. There is no limit on review rounds. End the loop only when the latest complete subagent review finds no new valid in-scope issues and every previously identified valid in-scope issue has been resolved, including issues introduced by fixes. A round with no new issues is not clean if an earlier valid issue remains unresolved. Required verification must also pass before completion or commit.
5. Bind the clean review to the exact file changes being delivered. Reinspect the full index before committing. File changes, payload drift or material context changes invalidate the review and restart the loop. Staging identical reviewed content alone does not require another round. Retain round identity, findings/dispositions, fixes, checks and reviewed content fingerprint in the external task record or, for Light work, a concise conversation record.

Use real subagent delegation; inline self-review cannot substitute. If delegation is unavailable, a review is partial, verification fails, intent is uncertain, or repeated attempts cannot progress, stop before completion or commit and report the concrete blocker. Never treat a round limit, elapsed time or an unchanged repeated finding as a clean result. Material uncertainty requires clarification rather than guessing. A read-only reviewer never fixes or publishes; the parent implements authorized fixes and requests a new review.
