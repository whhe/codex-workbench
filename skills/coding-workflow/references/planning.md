# Independent Plan Review Gate

Apply before modifying source, scripts or tests in every coding task, including tiny changes, behavior-preserving refactors and tasks needing no new test code. The trigger scope is identical to precommit-review.md. Content-only work and read-only investigation do not trigger either code gate. Plan review precedes code edits; code review follows implementation. Neither substitutes for the other or grants commit/publication authority.

## Clarify and Draft

1. Inspect relevant context read-only. Establish the overall goal, observable acceptance conditions, authorized scope, exclusions and user constraints under the entrypoint's goal rules. If those are too vague to choose a correct change, ask before modifying task files. Record unresolved questions and their dependent decisions; safely independent investigation may continue.
2. An explicitly authorized implementation task permits planning and implementation without routine user sign-off on the plan; discussion-only requests follow the entrypoint's discussion path. Ask only for missing facts or decisions that affect correctness, scope or intent; the task phase still controls commit/push confirmation separately. Draft the smallest plan that meets the goal: intended behavior, relevant interfaces or affected areas, implementation steps, known risks and verification. Consider the user's proposed approach, explain material conflicts or alternatives, and ask where a user choice is needed. For a tiny change the plan may be a few sentences; keep the review gate even when the plan is short.
3. State whether test code is needed using engineering.md's verification rule. Identify the meaningful unverified risk a new test would protect, or explain why existing checks and inspection suffice. Additional tests or abstractions are not plan improvements without a task-relevant reason.

## Review and Refine

1. Give a new independent read-only subagent the original request, confirmed goal/acceptance/scope, user constraints, current plan and relevant repository context. Use a fresh context; do not prime it with an intended verdict, earlier review conclusions or the implementer's defense. Have it select applicable specialist skills under the entrypoint's selection rules.
2. Ask it to challenge goal alignment, misunderstood requirements, missing steps, boundary cases, feasibility, unnecessary complexity, scope expansion and verification adequacy. Require concrete evidence and impact for actionable concerns. Return unresolved user decisions to the parent; the reviewer does not modify code, contact the user or authorize scope changes.
3. Assess findings against the goal and actual context. Refine the plan for valid in-scope issues. Explain false positives with evidence; defer unrelated suggestions. Ask the user before resolving a material unknown or expanding scope; pause dependent work while continuing safe investigation. For structured requirement discussions, prefer a suitable questioning skill from the available catalog. This helper is optional: if unavailable, ask directly; never guess the answer or install a helper without authorization.
4. After any plan adjustment or material clarification, dispatch a new independent subagent with the entire current plan and original goal again. There is no limit on review rounds. End the loop only when the latest complete review finds no new valid in-scope issues and every previously identified valid in-scope issue has been resolved; unresolved user decisions still block implementation. A round with no new issues is not clean if an earlier valid issue remains unresolved. Elapsed time or a repeated unchanged concern does not constitute acceptance. If review is unavailable, partial or cannot progress, report the blocker and do not begin dependent code edits.
5. Keep the reviewed plan, goal, acceptance conditions, review identity and dispositions in the conversation for small tasks, or existing external task storage when persistence is needed. Do not create workflow records in the code repository. Begin implementation only after this gate passes; a clean review does not resolve missing user authority or replace a required user confirmation.

## Preserve Alignment During Implementation

Before acting on a review finding or changing the approach, compare the proposal with the overall goal and reviewed plan. Ordinary fixes already within the reviewed approach do not restart planning for each edit. Material changes to the approach, affected boundaries or verification strategy require plan refinement and a fresh complete plan review before the dependent edits. User changes to the goal or acceptance conditions explicitly update the reference and invalidate affected plan conclusions. Preserve unrelated work and report gaps rather than broadening the task on a reviewer's authority.

After implementation, enter precommit-review.md for the independent code review/fix loop. Continue checking goal alignment on each round. Having no new tests does not waive either gate.
